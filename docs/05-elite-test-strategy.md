# Elite 系统测试策略

## 1. 测试策略概述

### 1.1 测试目标

针对 Elite 系统的两种架构模式，建立全面的白盒测试体系：

| 测试目标 | 描述 |
|----------|------|
| **功能正确性** | 验证业务逻辑在正常和异常情况下的正确性 |
| **数据一致性** | 确保数据库、Kafka、对账台数据一致 |
| **可靠性** | 验证消息不丢失、不重复、可恢复 |
| **实时性** | 验证 WebSocket 推送的及时性和准确性 |
| **幂等性** | 验证重复消费不会产生副作用 |

### 2.3 数据一致性验证策略

```
┌─────────────────────────────────────────────────────────────────┐
│                 架构1 数据一致性检查点                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  检查点 1: stp_generate_ticket ↔ stp_generate_ticket_audit     │
│  ─────────────────────────────────────────────────────────────  │
│  验证 SQL:                                                      │
│  SELECT t.event_id, t.status, a.status as audit_status         │
│  FROM stp_generate_ticket t                                    │
│  LEFT JOIN stp_generate_ticket_audit a ON t.event_id = a.event_id│
│  WHERE t.status = 'SENT' AND a.event_id IS NULL;               │
│  -- 结果应为空（已发送的消息必须有审计记录）                     │
│                                                                 │
│  检查点 2: stp_generate_ticket_audit ↔ Kafka offset            │
│  ─────────────────────────────────────────────────────────────  │
│  验证逻辑:                                                      │
│  • 对比 audit 表中的 kafka_offset 与实际 Kafka offset          │
│  • 确保每条审计记录对应一条 Kafka 消息                          │
│                                                                 │
│  检查点 3: stp_generate_ticket ↔ stp_ticket                    │
│  ─────────────────────────────────────────────────────────────  │
│  验证 SQL:                                                      │
│  SELECT t.event_id, t.status, k.ticket_id                      │
│  FROM stp_generate_ticket t                                    │
│  LEFT JOIN stp_ticket k ON t.event_id = k.event_id             │
│  WHERE t.status = 'COMPLETED' AND k.ticket_id IS NULL;         │
│  -- 结果应为空（已完成的必须有 ticket 记录）                     │
│                                                                 │
│  检查点 4: 状态一致性                                           │
│  ─────────────────────────────────────────────────────────────  │
│  验证逻辑:                                                      │
│  • PENDING: 无 audit，无 ticket                                │
│  • SENT: 有 audit，无 ticket                                   │
│  • COMPLETED: 有 audit，有 ticket                              │
│  • FAILED: 有 audit，audit.status = FAILED                     │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

```
┌─────────────────────────────────────────────────────────────────┐
│                    故障注入实现方式                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. Testcontainers 原生支持                                    │
│  ───────────────────────────────────────────────────────────── │
│  // 停止容器模拟宕机                                            │
│  kafkaContainer.stop();                                        │

│  // 暂停容器模拟网络延迟                                        │

│                                                                 │
│  // 断开网络模拟网络分区                                        │
│  dockerClient.disconnectFromNetworkCmd()                       │
│      .withNetworkId(networkId)                                 │
│      .withContainerId(containerId).exec();                     │
│                                                                 │
│  2. Toxiproxy 故障注入代理                                     │
│  ───────────────────────────────────────────────────────────── │
│  // 添加延迟                                                    │
│  proxy.toxics().latency("latency", ToxicDirection.DOWNSTREAM,  │
│      1000); // 1 秒延迟                                        │
│                                                                 │
│  // 模拟连接中断                                                │
│  proxy.toxics().timeout("timeout", ToxicDirection.DOWNSTREAM,  │
│      5000); // 5 秒后超时                                      │
│                                                                 │
│  // 模拟丢包                                                    │
│  proxy.toxics().bandwidth("bandwidth", ToxicDirection.DOWNSTREAM,│
│      0); // 带宽设为 0                                         │
│                                                                 │
│  3. Mock 服务配置                                              │
│  ───────────────────────────────────────────────────────────── │
│  // WireMock 配置延迟响应                                       │
│  stubFor(post(urlEqualTo("/api/payment"))                      │
│      .willReturn(aResponse()                                   │
│          .withStatus(200)                                      │
│          .withFixedDelay(5000))); // 5 秒延迟                  │
│                                                                 │
│  // WireMock 配置错误响应                                       │
│  stubFor(post(urlEqualTo("/api/payment"))                      │
│      .willReturn(aResponse()                                   │
│          .withStatus(500)                                      │
│          .withBody("{\"error\": \"Internal Error\"}")));       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```
